# JED / SED plug-in capability audit — 2026-09-30

The best route is to recover useful functions as shared, typed editor commands and reusable recipes, exposed to both people and agents. Loading historical plug-ins is a separate compatibility project and does not automatically make their GUI workflows scriptable.

This is a research milestone, not a new implementation or release. Current editor source was inspected at `83b158ce9e1aa9d79bb5bc51d3b3b25633e3357c`; the paused PLAY-01 package remains `00e7741990aa2b3e48e938136da0a383c5241782`. No legacy plug-in was installed or executed, and no paused reviewer request or publication was resumed. Raw downloads, forum pages, source extracts and acquisition receipts remain outside this repository. This report contains original analysis and public source links, not copied Discord logs or forum posts.

## Search coverage and limits

- Enumerated the complete current [Massassi plug-in catalog](https://www.massassi.net/jedplugs/): 39 linked ZIP entries after the editor itself, comprising 36 existing plug-in archives and three separate source links. Archive entries are not distinct product counts; packs contain multiple tools and source archives can duplicate the same product.
- Surveyed all 14 [JKDF2.NET tool-catalog pages](https://www.jkdf2.net/download-category/jkdf2-tools/) and 50 JED plug-in detail pages, then the [JKArchive tools mirror](https://jkdf2.net/JKBot/JKArchive/JKDF2/JKDF2/Game%20Files/tools/), including its JKE/JED Plugins directory. Checked author/mirror leads and earlier acquired tools without summing overlapping collections as new discoveries.
- Retrieved all 96 index pages across Massassi JK/MotS Editing, COG, Showcase and Discussion: **46,806 distinct thread titles/URLs**. Title screening selected 81 candidates, followed by 71 first-page acquisitions and ten continuation/supplementary pages. Selected content was inspected. This is **not** a claim that all posts in those threads were read. Generic titles, deleted attachments, separately archived older boards and unavailable mirrors remain coverage gaps.
- Surveyed 25 public repositories and relevant SED fork/SDK branches, recording commit identities and selected source/license evidence. These include editors, actual plug-ins, scripting wrappers, asset adapters and COG tools; they are not 25 interchangeable SED plug-ins or 25 fully audited codebases.
- Compared the findings with current Core, Formats, GUI and automation code. The fork exposes **32 named edit operations** through the Agent protocol and **11 MCP tools**. Source presence, reachable UI, tested behavior and complete agent workflows are classified separately.

The catalog consolidates the legacy downloads into **45 plug-in/companion families and three adjacent importer families**. The source supplement records **24 capability candidates**, some overlapping those families; these counts must not be added as unique products. The [machine-readable catalog](JED_SED_PLUGIN_CATALOG_20260930.json) preserves individual names, versions, public references, archive hashes, repository pins, source/reuse evidence and limitations. Its priorities are audit judgments, not implementation status.

The detailed local evidence root is `sed-editor-audit/plugin-audit-20260930/`, with disjoint `legacy`, `sources`, `forums` and `local` subdirectories. Downloads have URL/byte/hash records; archive integrity, source availability, reuse notices and actual runtime compatibility remain separate observations. This is a broad inventory of the known, reachable ecosystem, not a guarantee that no private or lost plug-in exists.

## Source recovery and reuse classification

All 36 original plug-in ZIP hashes match the prior acquisition records. A fresh source-extension scan corrects the earlier inventory: **ten source members in six archives**, including five Delphi `.dpr` files previously missed. These are Cleave2VX, MoveSC2VX, ThingPack, Flagman, MiniPlugins and SkyFlagger. Source in an archive does not by itself grant permission to transplant it.

The legacy catalog pass downloaded 26 additional ZIPs representing **20 distinct hashes beyond the original 36-file collection**; that baseline excludes other earlier research collections. Its 62 physical archive records contain 56 distinct hashes, of which 54 pass ZIP integrity checks. Point Extruder's document has a CRC failure and Ripper's descriptor has a header error. Fun3DO 0.5's update passes container integrity but contains a zero-byte executable. No binary was executed. The CleaveLight source and SurfaceTools releases recovered by the source lane are separate from these legacy-lane totals.

Version labels overstated some discoveries: Layer Everything is byte-identical to JedP, Stair Crazy's purported newer “Version 2” matches the already-held archive, and the two Free Sector 1.02 archive names have identical bytes. Useful distinct recoveries include Goal! 1.2 beta, Vinkel 1.01 with its separate source, Lighter .7, CreateVertex, ForceRemap 1.1 and Terraining .3. Massassi's Cleave2VX catalog says “surfaces”; the original Pascal header and other catalog establish **two vertices**.

The three dead Massassi source links—JKTree, SecCleave and Vinkel—were recovered from another public archive. The original CleaveLight C++ source was also recovered from the author's linked location. These are meaningful recoveries, with notices assessed separately. SecCleave has a noncommercial restriction; Vinkel source asks for prior permission. Do not classify either as GPL-compatible based on availability.

[ForceRemap's author announced a GPL source release](https://forums.massassi.net/Editing_Forums/Jedi_Knight_and_Mysteries_of_the_Sith_Editing_Forum/thread_11833_page_1.html), and its recovered binary package contains an explicit GPL notice. Matching implementation source was not recovered in this pass. That is a good source-recovery lead, not a completed code port.

[SurfaceTools-Plug-in](https://github.com/JKBoBoFett/SurfaceTools-Plug-in) has a public repository but its inspected branch is documentation-only. The two release ZIPs contain binaries rather than implementation source, and no general reuse grant was found. [JED Light Baker](https://github.com/LadyEebs/JED-Light-Baker) has substantial C++/HLSL source, but no project-wide reuse grant was established in inspected files. Both remain useful behavior/reference candidates; any implementation here should follow its own specification unless the required permission is established.

Concrete source candidates with observed grants include [Gorc](https://github.com/jdmclark/gorc) (Apache-2.0 COG parser/compiler), [JKL2OBJ](https://github.com/tyduptyler13/JKL2OBJ) (MIT geometry/UV exporter), [jedlib](https://github.com/colin-hurley/jedlib) (MIT OLE wrapper), [gimp-ijim](https://github.com/smlu/gimp-ijim) (MIT MAT code), [blender-sith](https://github.com/smlu/blender-sith) (GPL-3.0-or-later 3DO/KEY bridge), [jediknight2blender](https://github.com/Ecki81/jediknight2blender) (GPLv3-or-later importer entrypoint) and [Matt](https://github.com/bahstrike/Matt) (GPLv3 file). These still require component attribution and format/engine validation for the specific code proposed for reuse. In particular, IJIM-specific format and naming rules must not silently become MotS rules. The actual gimp-ijim LICENSE is MIT despite GitHub's NOASSERTION metadata.

Parsec's bundled source/readme identifies **1.8.0 FreeBASIC**, although its repository description still refers to 1.7.0 ancestry. No general reuse grant was found. All four returned public SED forks and eleven branch heads match the prior audit; this pass found no new fork implementation delta. ForceRemap's inaccessible author site, unavailable Code Alliance/dr0id/Nar Shaddaa/old JKHub routes, bounded archive-query failures and restricted GitHub repository search remain explicit recovery gaps.

**MAT16 correction:** its default [`main` at `4447216`](https://github.com/JKBoBoFett/MAT16/tree/444721680d07c239e6b7979eea972982309699c8) contains seven documentation/image files, but the [`V1.04` tag at `3b53c7c`](https://github.com/JKBoBoFett/MAT16/tree/3b53c7c20d2e5feb761ea6895bd2a1cb92eee6b7) contains Delphi/VCL implementation. The September 25 acquisition already included `Mat16.DPR`, `MAIN.PAS` and `EditMTS.pas`; their SHA256 hashes were reverified on September 30 and are recorded in the structured catalog. The tagged entry point starts the GUI, and the inspected batch handler loads `.mat16s` recipes through dialogs. This establishes selected implementation and a GUI recipe workflow, not a complete build acquisition, verified unattended CLI or executed conversion. The `master` implementation at `e0c860b113a061822b0550f224e7ce90b60bda48` was inventoried through metadata only. No general reuse grant was found in the inspected source and documentation. The separately acquired Mat16 1.1 binary remains a distinct artifact.

Use the actual GPL notices in SED and appropriately licensed related tools for scoped ports with attribution and dependency review. Keep unknown, permission-required and noncommercial code out of a blanket source-copying plan. Independent recreation means writing to documented behavior and original tests; this audit does not claim a formal clean-room process after source inspection.

## Compatibility findings that affect the design

1. **Legacy binaries are not managed plug-ins.** Current `Sed.App/PluginHost.cs` instantiates `ISedPlugin` managed assemblies. Historical tools use OLE `JED.App`, native IJED entry points, or the different native SED interface. Bitness, calling convention, string/record layout, ownership, editor state and GUI dialogs all matter. A new MCP wrapper would not remove those differences.
2. **The managed API is currently GUI-oriented and trusted.** `Sed.Plugins/ISedPlugin.cs` exposes the live mutable Level, SelectionSet and EditHistory through an `Action<PluginContext>`. It lacks typed request schemas and structured effect receipts. AssemblyLoadContext separates dependencies; it is not a security sandbox. Catching a plug-in exception does not automatically roll back earlier mutations. Prefer shared domain commands and the existing plan/apply path.
3. **A legacy MotS RGB readback defect remains visible.** Upstream `smlu/SED` at `c3b6c0e59f192e96dc6df2daf698fb179e63603a`, and the retained Pascal tree here, set `b := tv.color.g` in `TCOMLevel.SurfaceGetVertexLight` (`src/JED_COM.PAS:762–769`). The adjacent setter writes blue correctly. This was independently source-checked, not executed through a legacy plug-in. It does not establish a defect in our C# model or MCP channel. [Pinned source](https://github.com/smlu/SED/blob/c3b6c0e59f192e96dc6df2daf698fb179e63603a/src/JED_COM.PAS#L762)
4. **Partial feature overlap must stay explicit.** Our `AutoTextureCommand` fits individual faces using three unsigned dominant-axis projections; that is not ForceRemap's selection-wide UV workflow. Core cleave refuses crossed portals. Existing clipboard lacks placed COG capture. These are substantive missing contracts, not just missing toolbar buttons.
5. **Historical lighting reports supply counterexamples.** Lighter's author documented coplanar light/adjoin trouble and earlier RGB interface problems; later users described heavy cleaving and difficult subsequent edits. Preserve these as original fixture requirements, not claims about present runtime behavior. [Coplanar fix](https://forums.massassi.net/Editing_Forums/Jedi_Knight_and_Mysteries_of_the_Sith_Editing_Forum/thread_34599_page_1.html), [workflow report](https://forums.massassi.net/Editing_Forums/Jedi_Knight_and_Mysteries_of_the_Sith_Editing_Forum/thread_55641_page_1.html)

Current feature anchors: `dotnet/src/Sed.Formats/Automation/AgentWorkspace.cs`, `AgentQueries.cs:265–291`, `AgentSchema.cs:109–140`; `dotnet/tools/Sed.Mcp/ToolCatalog.cs`; `dotnet/src/Sed.Core/Editing/LevelClipboard.cs`, `TextureCommands.cs`, `CleaveCommand.cs:100–104` and `CleaveSectorCommand.cs:109–112`. GUI source includes a COG-generator window without a detected constructor call site; do not promise that workflow until its route is verified. Generalized flag filters should make any/all/none explicit, because current Core `FlagsMatch` uses any-bit matching.

## Recommended implementation order

**TOOL-01 — shared workbench and placement commands** is the next proposed feature milestone after the paused PLAY handoff:

1. Add efficient exact selection/filtering by material, template, layer and explicit flag predicates. Current paginated queries plus client filtering already work for many small tasks.
2. Implement reusable batch UV projection/transform and masked-property recipes. Surface the existing world-light bake through an explicit agent contract, and add report-first cleanup diagnostics. Preserve source/resource revisions and exact plan/apply/reopen effects.
3. Add sector/surface-relative placement, then bounded linear/grid/radial thing and light arrays. Specify basis, pivot, orientation/roll, count, clearance and containment; seed and version any stochastic recipe.
4. Build typed reusable prefabs and geometry arrays only after internal/external COG references, resource conflicts and reciprocal portal changes are accounted for. Use these invariants for connected stairs and later curved geometry.
5. Develop original MotS objective/door/lift/cutscene and water/glass portal recipes on the completed typed-COG and frame commands, with engine-profiled COG diagnostics. The result needs exact multi-file output/asset receipts and scenario-specific engine checks.

Run material-aware and model/ARCH lighting as its own milestone. Sun/sky/emission/bounce recipes require actual resource color/alpha and occluder semantics, explicit bake profiles and independent scalar/RGB handling. Keep retail and OpenJK comparisons separate. The Light Baker README itself documents limitations around 16-bit material fill colors; it is a source of requirements and counterexamples rather than proof of full MotS parity.

Every new shared operation should have a stable schema, bounded resource/time cost, a deterministic plan or recorded seed, undo/redo, failure rollback, source/resource identity guards and structured before/after effects. GUI controls and `sed_plan`/`sed_apply` should call that same implementation. **No additional generic MCP server is required for this plan.** An optional out-of-process legacy host could be considered later for a specific otherwise-unavailable capability, with original fixtures and verified host/API semantics.

Acceptance should include deliberately adverse geometry/reference cases, not just successful examples: different R/G/B, zero and inherited light channels, portal-plane lights, reflected winding, intentional translucent/secret walls, malformed resource references, same-name changed assets, overflow budgets and failure partway through a compound operation. Structural and rendered results must remain distinct from native gameplay or retail compatibility.
