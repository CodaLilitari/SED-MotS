# SED MotS data, plugin, episode, and template audit

Audit date: 2026-09-08. Starting SED revision: `c3b6c0e59f192e96dc6df2daf698fb179e63603a`.

This is a source audit and a tested set of bounded data fixes. It does not certify a complete SED GUI build, lossless import/export, retail playthrough, or OpenJKDF2/OpenMotS runtime compatibility. The editor still requires Delphi/VCL to build in full. The tests below compile actual independent production logic with native Windows Free Pascal; additional harnesses compile exact production include bodies with small data-only class scaffolding.

## Implemented changes

| Finding | Evidence and correction | Validation |
|---|---|---|
| Both old plugin interfaces created the opposite project type | `TJEDCOM.NewLevel(mots)` and `TJEDApp.NewLevel(mots)` dispatched `true` to `New1` and `false` to `NewMotsProject1`. They now dispatch `true` to MotS, consistently with both interfaces' existing `SetIsMots` methods. | Source/control-flow review. Full DLL/OLE invocation awaits the VCL build. |
| Legacy JED MotS light colors were silently misread | The old loader first tried a 10-field SED scan on a 12-field JED row. `SScanf` accepts trailing fields, so RGB range/intensity became red/green and actual red became blue. Its fallback also read a second line instead of retrying the same row. `EditorDataIO.ParseEditorLightData` now classifies exact field counts and the stream reads one row per light. | Native tests cover current/legacy rows with distinct color/control values, hexadecimal flags, comments, whitespace, locale independence, malformed counts and values. |
| Legacy MotS colored relighting used the wrong control after the format migration | NJED's old lighting code uses primary `range` for both channels, scalar `Intensity` for the white channel, and `RGBIntensity` for RGB. SED's MotS light calculation has one intensity and computes RGB. Legacy MotS now maps `RGBIntensity` into that control; JK retains primary intensity. Primary range is retained. | Actual production helper tests cover differing white/RGB intensities and ranges and both project choices. Independent white control cannot be retained in SED's current model; one import warning discloses affected lights. |
| Malformed JKL lighting cardinality could index beyond the parsed list | The old loader interpreted any count greater than the vertex count as colored lighting, then indexed three or four values per vertex. It now validates exactly one component per JK vertex, four per MotS vertex, and three per IJIM vertex before indexing. The temporary lighting list is freed on exceptions. | Native checks include valid triangle/24-vertex layouts, incomplete/excess tuples, invalid versions and overflow-sized counts. |
| An unknown sector property could itself break the warning path | `LoadSectors` used `jsurf.sector.num` before a surface necessarily existed. Diagnostics now use the known sector-loop index. A premature section boundary stops this sector import with an explicit diagnostic, exceptions are reported instead of swallowed, and the lookup list is freed in `finally`. | Source/control-flow review; this does not make the whole JKL importer transactional or validate every index. |
| Episode creation/save could retain stale state or discard the current edit | `CreateNewEpisode` did not initialize episode name/type; defaults now reset to `New Level` and single-player `TYPE 1`. Saving commits the focused sequence. The shared string editor first receives the focused detail edits, then refreshes those controls on return so final Save does not overwrite its changes. Empty sequence lists no longer index item zero, adding to an empty list works, and empty briefing text does not index `Lines[0]`. Editor state is released in `finally`. | Source/control-flow review, including the string-editor synchronization regression found by peer review; modal UI and filesystem save workflow await VCL validation. |
| Reassigning a template retained freed value pointers | `TTemplate.ClearVals` freed values but did not empty the list. Assignment now clears the list before adding clones and explicitly tolerates self-assignment. | Exact production methods executed with instrumented values; replacement, deep-copy independence, repeated assignment, self-assignment, repeated clear and destruction tested. |
| Deleting a custom template corrupted subsequent name lookups | `TTemplates.DeleteTemplate` removed the list element but left the sorted name table's later numeric indexes unchanged. All shifted indexes are now decremented. A list destructor also releases the owned template/name structures. | Actual methods tested with alphabetical order different from insertion order, middle/first/last deletion, surviving lookup identities and object ownership. |
| Three bundled JK lightning templates were unparsable | `data/master.tpl` concatenated `+force_lightning2/3/4`, the parent name and `damage=` into a single token. Only the missing whitespace was repaired; the existing 15/20/25 damage values were retained. | Structural audit covers every bundled JK/MotS template definition, parent chain and declared template-valued field. |
| MotS architectural model lighting and its thing bindings were discarded | The loader now retains the MotS thing column and parses `ARCHLIGHTING`. Each thing owns its binding; the level owns the lighting data. Native project sections persist the lighting, binding and source-model identity. JKL export writes verified bindings and the stored mono/RGB components. Same-level duplication and undo preserve binding metadata; clipboard copying warns that its legacy binary format omits it. | Native parser tests and exact integration methods cover persistence, reordering, cache lifetime and safe export decisions. The separate engine audit verifies all 39 playable stock MotS sections and 2,353 bindings. Duplication/undo/clipboard wiring was source-reviewed, not run in VCL. |
| Replaced models could receive incompatible baked architectural lighting | Import records the source model name and a SHA-256 of normalized model text. Export resolves the current active template, checks the name and hash, requires exact highest-detail mesh/vertex counts, and checks coverage for every lower-detail geometry set. Failed verification emits a warning and exports an unbound thing while preserving the original native data. | Integration checks include missing models, changed names, same-name/same-shape changed vertex content, expanded/shrunken meshes, missing source identity and invalid indexes. The FPC scaffold exercises content identity through a test hash facade; it does not execute Delphi's SHA-256 implementation. |
| Local template inheritance could fail at a globally defined parent | The source-model getter now resolves each ancestor against level-local and active game templates. Export uses the active template list, so template edits cannot be masked by the imported snapshot. Thing overrides remain first; missing parents and cycles terminate safely. | The exact production getter passes 13 checks, including mixed local/global inheritance, overrides, case-insensitive names, active-template edits, missing parents, cycles and no owning level. |
| Scalar-only MotS geometry was resolved as JK before later format evidence | An independent preflight detects a real `SECTION: ARCHLIGHTING` header before main parsing and resource resolution. The main parser also treats architectural data as a positive MotS signal. Both architectural section wrappers require their actual `END` terminator. | Source review for the independent JKL preflight; exact native-reader tests cover the next-section boundary, missing `END`, truncated sections and atomic binding failure. Scalar-only files without positive MotS format evidence remain ambiguous. |

## Tests executed

Native compiler: Free Pascal 3.2.2, Windows i386, using Delphi Unicode mode and enabled range/overflow checks. The production `EditorDataIO` unit compiles without warnings; Free Pascal reports some string-conversion warnings in the harnesses and a hidden-method warning matching the existing template class declaration. These are not a Delphi build result.

- `tests/test_mots_data.dpr`: **59 checks passed**, including a fresh output directory with explicit unit paths and no broad source search path.
- `tests/test_template_state.dpr`: **34 checks passed**. An additional `-gh` run reported **171 allocations, 171 frees, 0 unfreed blocks** for that harness.
- `tests/test_archlighting_integration.dpr`: **55 checks passed**, with **2,932 allocations, 2,932 frees, 0 unfreed blocks** under `-gh`. This compiles the exact production capture/validation, native binding serialization/parser, and native section-reader bodies. It tests declared-count errors (including negative, huge and overflowing values), duplicate bindings, truncated input, preserved source metadata after failed verification, and bindings following thing order changes.
- `tests/test_thing_model.dpr`: **13 checks passed**, with **319 allocations, 319 frees, 0 unfreed blocks** under `-gh`. This compiles the exact production model-name getter.
- `tests/test_archlighting.dpr`, owned by the parallel engine audit: **71 checks passed** for the pure production section and model-topology parser. The separately documented stock-data run preserved **154,488 scalar/RGB components across 38,622 vertices** in all **39 playable MotS levels** and validated **172 unique bound model files**, with zero highest-detail shape or lower-detail coverage mismatches. See [retail architectural-lighting evidence](retail_archlighting_evidence.json).
- `python tests/audit_template_data.py --check`: **656 JK templates and 774 MotS templates**; zero duplicate names, malformed rows, missing parent/declared-template references, or parent cycles after the whitespace repair. This does not resolve model, COG, sound, or texture files from a game installation.
- `git diff --check` passed for the data/plugin/episode/template and architectural-lighting integration changes.

The template harness includes `src/TEMPLATE_MUTATIONS.INC`, which is also included by the production `U_TEMPLATES.PAS`; it does not carry a second implementation of the changed methods. Other types in that harness are deliberately small test scaffolding, so this remains narrower than running the editor's complete template subsystem.

The architectural integration harness similarly includes `ARCHLIGHTING_IO.INC`, `ARCHLIGHTING_BINDINGS.INC` and `ARCH_NATIVE_READ.INC`. Its fake game-file registry supplies model text, and its FPC `THashSHA2` facade uses MD5 solely to test whether content identity is compared and preserved. Production uses Delphi `System.Hash` SHA-256. This harness does not execute the complete JKL/native save procedures, actual archive resolution, VCL controls, clipboard, undo stack, or Delphi hashing. `test_thing_model.dpr` separately includes `THING_MODEL_IO.INC` so model inheritance is exercised through the production getter instead of that integration scaffold's fixture getter.

Architectural source hashes remove comments, surrounding line whitespace and blank lines; they retain interior whitespace, case and all remaining model content. This is deliberately conservative: a harmless interior-formatting change can require a fresh verified import. A matching hash certifies continuity with the model available at import, not that an arbitrary imported level's lighting was originally baked against that model. Highest-detail topology checks and lower-detail coverage checks provide the separate bounds safeguard.

## Already correct or intentionally preserved

- JKL vertex lighting currently loads and writes MotS tuples as intensity, red, green, blue. The local engine's `src/World/sithSurface.c` reads that same tuple order and stores the channels in separate internal arrays. Export component order was preserved.
- The native JED/SED project file stores per-vertex scalar values followed by separate RGB values. Those imported baked values are not recalculated by the legacy light migration. A later lighting calculation is a new computation, with the disclosed legacy white-control limitation.
- SED already copies surface extra light from the temporary imported surface into the level object. The omission identified in JED/NJED's import path is not present here.
- SED's current `TSedLight.Assign` copies the complete color record, flags, range and position. It does not retain the older NJED blue-from-green assignment error.
- Project template selection uses `mots.tpl` for MotS, `master.tpl` for JK, and merges level-local templates over the selected base. The stock MotS `walkplayer` definition references `kyle_m.cog` and `kk.3do`, unlike the JK definition. Asset paths and definitions were preserved.
- Resource dependency compilation reads `items.dat` through the configured game-file resolver and follows declared COG/template dependencies. That behavior is preferable to guessing MotS inventory definitions in the exporter.

## Remaining high-priority limits

1. **Architectural lighting is preserved with verification limits, not newly baked.** The previous unconditional discard is fixed. Moving/rotating things can still make their baked lighting look stale, and this pass adds no architectural relighting UI. If the source model cannot be verified at import, the native project retains its original data but JKL export omits the binding; reimport with the correct assets available establishes the baseline. Clipboard paste deliberately stays unbound and warns. Opening and saving these native projects with older SED versions can discard the new sections. Full editor and engine rendering validation remains outstanding. See [engine contract audit](ENGINE_CONTRACT_AUDIT.md).
2. **The startup COG generator remains JK-oriented.** `U_COGGEN.PAS` hardcodes weapon/ammunition bins and `jkSyncForcePowers` without a MotS profile or an inventory reader. Its UI lacks a deliberate MotS weapon/Force layout. The correct expansion needs authoritative `items.dat`/COG definitions and game execution, not renamed checkboxes or guessed bin numbers.
3. **Project autodetection is still ambiguous without positive format evidence.** An `ARCHLIGHTING` section now selects MotS before resolving COGs/assets even when surfaces contain only scalar values, and four-component vertex rows remain a MotS signal. A scalar-only version-1 level with no architectural section or other MotS-only field still needs an explicit import target. Filename guessing is insufficient; that import-target UI is outside these data changes.
4. **Importer failures can still leave a partial level.** Many legacy scans and index lookups are unchecked, outer handlers report rather than roll back, and source sections not represented by the object model may be dropped. The new cardinality checks protect a specific MotS path; they are not a full parser rewrite.
5. **Legacy two-channel light controls cannot round-trip exactly.** The parser recognizes both controls and migrates the active colored-light parameters, but the SED light model and writer have one intensity/range. The old separate white intensity is disclosed, and the unused old `RGBRange` is not serialized. Keep original JED source when exact archival reproduction matters.
6. **Episode parsing and string writing need a separate hardening pass.** Existing code does not fully validate malformed sequence headers/rows, preserves only its modeled episode/string fields, and uses legacy text I/O. This pass fixes the ordinary UI data-loss/default cases; it does not claim atomic multi-file save or full custom Unicode/quoting behavior.
